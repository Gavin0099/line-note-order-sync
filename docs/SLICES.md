## S00：固定產品與資料基線

**目的**：讓首批程式有明確輸入、輸出與拒絕條件。

**範圍與交付**

- 建立 `pyproject.toml`、`src/notesync/`、基本 CLI 入口、`.gitignore` 與最小 CI 設定。
- `docs/PRD.md`：首個來源類型、單篇多 SKU、獨立喊單／追加／改單的處理邊界。
- `docs/DATA_CONTRACT.md`：來源範圍、可缺失原生 ID、完整性狀態、JSON 格式、
  TXT 分段規則、批次與解析版本、快照接受規則、報表條件。
- 商品 YAML 範例與合成 fixtures；真實樣本僅供本機確認複製格式並留在忽略目錄。
- S01 實驗記錄模板，包含環境、人工基準與能力矩陣。

**驗收**

1. Python 3.12 可安裝套件並執行 CLI help。
2. 用合成案例明確寫出：哪些直接解析、哪些待審、哪些無效、何時不能輸出正式報表。
3. 商品代號的來源範圍、重複留言、同名買家、無 ID、部分擷取均有預期行為。
4. 本機 DB、真實輸入、截圖、傾印與匯出路徑確實被 Git 忽略。

**停止條件**：資料契約仍以暱稱當唯一身分，或重匯與改單語意矛盾時，先修正契約。
缺少真實 TXT 樣本時可先完成結構化 JSON 契約，不宣稱原生複製格式已支援。

## S01：單篇記事本的唯讀擷取實驗

**目的**：在投入自動化前確認資料是否取得、是否完整，以及能辨識到哪種身分。

**前置**：由本人登入 LINE 並開啟有權讀取的指定記事本；記錄群組或 OpenChat 類型。
不讀取登入憑證、瀏覽器 profile、Token 或私人 API。這一片不寫入正式訂單資料庫。

**範圍與交付**

- 選用的 `windows_uia_probe.py`：限定 LINE 程序／目標視窗，先讀元素樹與文字 pattern。
- 操作者手動捲動／展開留言，probe 觀察結果；若要程式操作，只限載入、捲動與展開，
  禁止送出訊息、編輯或刪除內容。自動導覽不是這片的必要交付。
- `docs/CAPTURE_FEASIBILITY.md`：OS／LINE／probe 版本、範圍、步驟、結果與限制。
- 原文／元素傾印與人工對照留本機；repo 只留去識別結果與重現方法。

**實驗案例**

- 同一篇包含跨至少兩個可視區域的留言，人工基準宜達 30 筆；不足時明列覆蓋不足。
- 重複暱稱、相同內容、多行、全形字元、折疊回覆（若介面支援）、延遲載入及空篇。
- 記錄畫面顯示數量的語意，區分頂層留言、回覆與已刪除內容；數量相同不當作內容相同。
- 關閉再開同一篇、改變捲動位置後重讀，分別檢查 source comment/author ID 是否穩定。
  UIA RuntimeId、元素位置或暱稱不直接視為原生穩定 ID。

**驗收與決策**

1. 在指定案例與來源範圍內，逐筆比對作者標示、全文、邊界與順序，不只比總筆數。
2. 分別評定 `text_readable`、`full_snapshot_supported`、`completeness_detectable`、
   `stable_comment_id`、`stable_author_id`；每項可為 `YES`、`NO`、`UNKNOWN`。
3. `FEASIBLE` 指在記錄條件內完整快照可取得；即使沒有穩定 ID，也只能啟用快照核對模式。
4. `NOT_FEASIBLE` 指在所測版本與已嘗試方法內有明確阻礙；不是宣稱 UIA 永遠不可能。
5. 超過限時或基準不足無法判斷時記 `INCONCLUSIVE`，不得當成成功或全面不可行。

**停止條件**：缺頁、作者／全文不可讀、來源不明或無法判定完整時，不投入定期同步。
時限到即保留結論並繼續 S02；不自動擴大成 OCR、私人 API 或協定分析。

## S02：嚴格喊單 parser

**目的**：讓明確喊單得到確定結果，歧義文字不誤入訂單。

**範圍與交付**

- normalize、商品設定驗證與純函式 parser。
- 保存原文；只對解析副本做約定的全形／大小寫／空白正規化。
- 結果狀態至少區分 `PARSED`、`NEEDS_REVIEW`、`NON_ORDER`、`INVALID`，附理由。
- 多商品留言採整則判讀：含未知、疑問或取消片段時，不能只採信其中成功的 token。

**必要案例**

| 輸入／情境 | 預期 |
| --- | --- |
| `A+1`、`B+2` | 對應 SKU 與正整數數量 |
| `Ａ＋１`、約定的小寫／空白形式 | 正規化後相同結果 |
| `A+1 B+2`、約定的逗號／換行分隔 | 同則多 SKU |
| 裸 `+1` | 僅有明確預設 SKU 才解析 |
| `X+1` | 未知商品待審 |
| `A+0`、負數、小數、超過設定上限 | 無效或待審，不計入 |
| `A+1？`、`如果有貨 A+1`、引用別人的 `A+1` | 待審，不作局部命中 |
| `改成 A+2`、`取消 A`、`再一個`、同則重複 SKU | 待審 |
| 純感謝文字、空白、純貼圖描述 | 不建單，保留分類結果 |

**驗收**：固定的正反案例逐項比對，輸出包含版本與理由；parser 不呼叫 LINE、DB 或網路。
人工預期答案與案例一起提交，不用 parser 自己產生答案再測自己。

## S03：手動匯入與 SQLite 保存

**目的**：讓一份輸入能可靠落地，關閉重開程式仍可追溯與重跑。

**範圍與交付**

- Adapter 契約、UTF-8 JSON 匯入、第一種已確認的 TXT 格式與 CLI 匯入命令。
- 儲存原始輸入、來源範圍、原文位置、完整性、商品設定、parse run 與異常結果。
- SQLite foreign keys、必要唯一約束、schema 版本與單批交易。
- 同一輸入識別與 parser／設定重跑分開；UIA 資料日後也走同契約。

**驗收**

1. 合成輸入匯入後關閉 DB，再開仍能還原原文、版本與每筆解析來源。
2. 同 bytes 在不同 `note_key` 不混合；相同快照重匯不重複保存有效解析／訂單。
3. 相同原文的兩個 occurrence 均保留；缺失的來源 ID 仍為缺失。
4. 不合法格式、編碼或分段不明時，保留可回查錯誤並拒絕建立可接受快照。
5. 中途注入失敗後沒有半個可用批次或懸空明細；原本資料不變。
6. `PARTIAL`／`UNKNOWN` 可保存供核對，不能因成功寫 DB 就升格為完整。

## S04：冪等、人工核對與快照接受

**目的**：把解析結果轉成可信的目前訂單，並防止反覆同步誤計。

**範圍與交付**

- 待審清單與最小 CLI 審核操作：確認、標示非訂單、登錄人工判讀結果及買家對應。
- 每個人工決定附原值、結果、理由、時間與操作者；不可改寫原始留言。
- 明確選定某篇的 batch + parse run，以單次交易更新目前訂單投影。
- 新快照與原先快照列出差異候選；無 ID 時不得把候選稱為已確認修改／刪除事件。
- 阻擋性異常含作者無法對應、重複來源不明、未知 SKU、文意不明與完整性不足。

**驗收**

1. 同一批連續匯入／接受三次，數量、有效訂單筆數不增加。
2. 兩份完整快照從 A=2 變為 A=3，選用後為 3；歷史保留 2，不能得到 5。
3. 舊檔較晚匯入不自動取代目前快照；新 parser 結果也須重新接受。
4. 部分快照少了一筆留言，不刪除既有訂單、不推定取消，也不能成為目前正式依據。
5. 同名兩人分開；同人多則留言若追加／取代意圖不明先待審。
6. 相同內容多 occurrence 不被 hash 消除；疑似複製重疊未釐清則阻擋正式輸出。
7. 接受過程失敗時仍維持前一完整版本，不出現新舊混合結果。
8. 每筆目前訂單能回查快照、原文、parser／設定版本與人工決定。

P0 的人工判讀不代表已實作 P1 的來源編輯／取消事件追蹤。

## S05：CSV 與端到端 CLI

**目的**：完成日常可用、可核對的本機交付流程。

**範圍與交付**

- 買家／留言明細、商品統計、異常核對清單與來源 metadata。
- Metadata 至少記錄來源、選定 batch／parse run、輸入／設定雜湊、完整性與確認方式、
  接受時間、輸出時間與審核結果；原生 ID 缺失時清楚標示身分限制。
- 核對模式輸出明確標示草稿；正式模式只讀取已接受且符合條件的版本。
- UTF-8 BOM CSV、欄位引用、換行／逗號與公式字首防護；DB 原文不因匯出防護而改動。
- CLI 支援匯入、檢視、審核、接受與匯出，附一組可複製的合成範例操作。

**驗收**

1. 合成範例由匯入到正式匯出全程可完成，買家明細與商品統計對上人工答案。
2. 異常未解、完整性不足或未接受版本時，正式匯出失敗並給明確原因。
3. 僅接受部分資料的核對清單有可見標記與 metadata，不冒充完整叫貨單。
4. 同一接受版本重複匯出內容一致，允許輸出時間等 metadata 不同。
5. 中文、引號、換行、`=`／`+`／`-`／`@` 等危險文字欄位有可驗證的保護；
   僅把欄位加雙引號不當作公式防護。
6. 匯出取固定版本的一致讀取；寫檔失敗時不留下看似完成的正式報表套件。

CLI 具體命令名稱在 S00 定稿，這裡不提供尚不存在的執行指令。

## S06：單篇試用、交付與維護基線

**目的**：把開發機上的流程變成另一個乾淨 Windows 環境可使用的 MVP。

**範圍與交付**

- 安裝、設定商品、輸入格式、審核、匯出、資料備份與恢復說明。
- Python 套件交付與必要相依的可重建安裝；暫不要求打包單檔 EXE。
- 在有權處理的單篇實際記事本試用，人工逐筆核對，真實資料不提交 repo。
- Windows 核心測試 CI 設定與本機執行證據分開記錄；無遠端時遠端 CI 為 `NOT_RUN`。
- 已知限制與版本發布準備清單；發布程式版本前選定 LICENSE，檢查敏感資料與 Git 歷史。

**驗收**

1. 乾淨 Windows venv 可安裝、跑合成範例與核心測試；未安裝 UIA 相依仍可跑手動流程。
2. 單篇試用的明確訂單逐筆、逐 SKU／數量對上人工答案；未決資料不進正式總表。
3. 同批重匯、全新完整快照、部分新快照與 parser 重跑均符合 S04 語意。
4. 備份還原後能產生相同接受版本的報表，原文與人工決定可回查。
5. README 精確標示支援範圍與 S01 結論；不把本機通過寫成遠端 CI 或 UIA 已全面可用。

**完成界線**：完成的是手動 MVP 與限定試用；這片的完成條件不包含軟體版本發布、部署或啟用自動同步。
若缺本人登入或實際來源，可先完成合成驗證，但實際試用必須維持未完成。

## S07：有來源證據的改單／取消

**進入條件**：S06 完成；若要自動追蹤編輯／刪除，必須另外證明 source comment ID
與身分作用域穩定、來源變化可判定，以及快照完整性可核對。

**交付**：留言版本、明確改單／取消規則、變更預覽與人工確認、回歸案例。
沒有穩定 ID 時只增強人工核對；不能用文字相似度或暱稱假裝來源事件。

**驗收**：編輯、明確取消、刪除、追加、亂序觀察與部分擷取分開測試；
沒有觀察到留言不直接等於取消，有歧義就保留待審，所有變更留歷史。

## S08：定期擷取／同步

**進入條件**：S01 在指定來源可行、S06 完成，並已證明每批可判定擷取範圍與完整性。
自動更新正式訂單另須通過 S07 的來源能力與變更驗收；否則最多定期收集待審快照。

**交付**：單程序排程、重入鎖、timeout、有限重試、最後成功／失敗狀態與明確停用。
只讀取既有人工登入狀態；不自動取得或保存登入憑證。

**驗收**：鎖屏、登出、視窗不在、載入失敗、UI 改版、重啟與重複執行時不誤改訂單。
不完整或未知擷取一律停止接受，不把上一份報表標成新同步完成。
連續成功不是完整性證明；每一輪仍須符合當批證據條件。

## S09：Google Sheets 匯出

**進入條件**：S05 已有版本固定的正式輸出；試用前完成 S06。
此片與自動擷取獨立，可以在人工接受後更新 Sheets。

**交付**：標準授權流程、專用工作表、以內部訂單／版本 ID 更新的 adapter、執行紀錄。

**驗收**：同版本重送不增加重複列；部分遠端失敗可重試／核對；
