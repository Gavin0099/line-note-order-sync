# S00 產品基線

日期：2026-11-05。範圍：單人、Windows、本機 CLI；S00 只提供規格與套件入口。
驗收來源：owner 專案目標、最新暱稱決策及 PR #1 的審查修正。

## 使用者與流程

操作者管理 LINE 社群的商品記事本，需要核對喊單與叫貨數量。
MVP 流程為設定商品 → 手動匯入單篇完整快照 → 解析 → 核對異常 → 人工接受 → 匯出。
首個擷取實驗候選為 `line_openchat_note`；這是依「社群」目標選的暫定範圍，
本人仍須於 S01 確認實際來源類型、LINE 版本與指定文章。一般群組另做擷取驗證。
JSON 契約可描述這兩種來源，不表示兩種 UIA 能力已通過。

## P0 行為

- 一篇可有多 SKU；商品代號只在該篇設定內有效。
- 每則明確喊單代表該 occurrence 的數量；同快照內多則獨立喊單可相加。
- 支援 `A+1`、`B+2`、`A+1 B+2`、全形及明訂分隔符；裸 `+1` 需設定預設 SKU。
- 問句、未知 SKU、改單、取消、追加語意與同則重複 SKU 先待審，全文不作局部採信。
- 沒有原生作者 ID 時，可依同社群暱稱彙總，不要求逐則人工映射。
  同名預設合併、改名預設分開；接受其誤併／拆分風險，可人工拆分／合併並保留原文。
  不同社群不自動合併；暱稱分組不證明來源留言的穩定身分。
- 每篇只選一份完整且已接受的快照；新快照取代投影，歷史不刪，不累加兩份快照。
- 缺留言 ID 時只呈現跨快照差異候選，不能自動宣稱識別編輯、刪除或取消。
- 部分／未知完整性及阻擋異常可供核對，不能作正式叫貨報表。
- 人工宣告完整需方法與證據；報表本體明示 `HUMAN_DECLARED` 及來源時間。

## 手動輸入與操作成本

S03 首先實作 UTF-8 JSON；範例見 `tests/fixtures/manual_snapshot.example.json`。
真實 LINE 複製文字尚無樣本，TXT 的作者／時間／多行分段規則維持 `UNCONFIRMED`。
不先發明看似 LINE 原生的 TXT 文法，也不把 JSON 人工整理當作已證明節省時間。
S01/S06 記錄原整理、複製／匯入準備、核對耗時與異常比例；需要逐則重打時明列效益未證明。

## 驗收案例與完成邊界

- Parser 人工答案：`tests/fixtures/parser_cases.json`；數量上限 99 的邊界及拒絕案例已列。
- 買家與快照序列：`tests/fixtures/workflow_cases.json`；供 S03–S05 實作，S00 不執行這些功能。
- 50 則無作者 ID 明確喊單：`tests/fixtures/no_id_50.json`，預期同一暱稱 A=50；
  fixture 明確宣告 50 個獨立 occurrence，非複製重疊。此為合成答案，不是實機證據。
- S00 驗證套件安裝、CLI 成功／無效命令、無資料副作用、忽略路徑與人工案例一致性。
- S01 保持 1–2 工程日 timebox；擷取結論與手動核心獨立。
