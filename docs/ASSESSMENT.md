# 可行性與範圍評估

評估日期：2026-11-05，Asia/Taipei。

## 1. 結論

建議採用 `line-note-order-sync`、Python 3.12、SQLite 與 pytest，先做本機 CLI。
將留言取得、訂單解析、快照核對與報表分開，符合長期維護需求。

第一個可交付產品應是「單篇記事本的手動匯入、可追溯解析與核對報表」。
Windows UIA 另以限時實驗決定是否投入；目前不能承諾自動完整讀取或可靠辨識改單。
自建的理由成立於資料與規則的自主性，單靠節省月費則不足以證明開發回報。

5. **使用邊界**：服務條款列有不當 Bot 操作與非法蒐集第三方資訊等禁止行為。

## 4. 必須補上的六個設計決定

### 4.1 先選定來源與商品規則

一個商品記事本可以包含多個 SKU，但 `A` 只在該記事本的商品設定內有意義。
首個試點只選一種來源：`line_group_note` 或 `line_openchat_note`。
另一種來源需另做擷取驗證，不能沿用能力結論。

P0 明確文法採 `A+1`、`B+2`、`A+1 B+2`，支援約定的空白、換行、分隔符與全形字元。
商品設定需驗證代號唯一、別名不衝突、數量為有上限的正整數。
裸 `+1` 僅在該篇明確指定唯一預設 SKU 時可解析。
「再一個」「改兩個」「不要了」「A+1？」「如果有貨 A+1」均先待審。
第一版不需要 LLM 或外部 AI API。

### 4.2 將批次、留言與買家身分分開

- **批次／快照身分**：能辨識同一來源、同一輸入及同一解析設定的重匯。
- **留言身分**：原生留言 ID 若確實可取得才使用；缺少時只產生快照內的 occurrence ID。
- **買家彙總**：有可驗證的原生作者 ID 時優先使用；缺少時，MVP 依 owner 決定，
  可用同一 `scope_key`（單一社群）內的暱稱彙總，無須逐則人工建立 `buyer_key`。
  此為方便核對的分組，接受同名誤併、改名分組的風險，不宣稱是真實或穩定身分。
  不跨社群自動合併；報表保留內部買家鍵、原始暱稱與每筆 occurrence，允許人工拆分／合併。
  缺少作者 ID 本身不構成阻擋；作者標示空白或分段不明才需人工處理。

內容雜湊用於完整性與重匯檢查，不是留言或買家的可靠識別方式。
同一快照中兩筆完全相同的留言必須保留，不能直接消除。
無法判別它們是兩筆真實留言或複製重疊時，列入待審並阻擋正式報表。

### 4.3 P0 以選定快照重算，不把每次匯入相加

同一篇記事本一次只選一份已接受的完整快照作為目前訂單依據。
新快照不與舊快照相加；舊快照、原文與先前解析結果仍保留。
匯入時間不代表留言時間，較晚匯入的舊檔案也不能自動取代目前快照。

在沒有穩定留言 ID 時，操作者可以核對整份新快照後選用，
但系統只能宣稱「依此快照重新計算」，不能宣稱已識別某人的編輯、刪除或取消。
同一暱稱的多則獨立、明確喊單可累加於目前快照；「追加／取代」意圖不明仍待審，
不以最後一筆覆蓋前面。相同內容多筆仍依 occurrence 保留，複製重疊疑慮另行核對。

### 4.4 完整性是資料狀態

| 狀態 | 定義 | P0 可否直接成為正式報表依據 |
| --- | --- | --- |
| `VERIFIED_COMPLETE` | 在限定來源範圍內，有可核對的完整性證據，並記錄方法與限制 | 仍需完成解析與人工接受 |
| `DECLARED_COMPLETE` | 操作者宣告已完整整理；不等同機器驗證 | 可在明確確認與標示後使用 |
| `PARTIAL` | 已知截斷、漏頁或只選取部分留言 | 否 |
| `UNKNOWN` | 無法判定是否完整 | 否 |

有留言總數或捲到畫面底部都不足以單獨證明完整。
測試記事本應以獨立人工基準逐筆比對；實際擷取還需保存本次載入／範圍證據。
PoC 通過只代表該版本、來源類型與條件可行，不能自動把往後每一批標成完整。
完整性宣告若有更正，要保留更正紀錄，不能改寫原始輸入。
`DECLARED_COMPLETE` 必須保存操作者、宣告時間、人工逐筆核對方法與證據參照；
正式報表 manifest 與檔名都標示 `HUMAN_DECLARED` 及來源快照時間，
與 `VERIFIED_COMPLETE` 的驗證結果保持可見區別，不能只藏在 DB metadata。

### 4.5 區分核對輸出與正式輸出

部分或未知快照仍可產生明確標示的核對清單，但不能變成可直接叫貨的正式總表。
正式輸出需要：來源／記事本已確認、完整性符合上述規則、阻擋性待審為零、
有效商品設定、已接受的解析版本，以及操作者明確選定快照。
每篇記事本的接受範圍與狀態均列入輸出 metadata，不能只在終端顯示提醒。

遇到不完整的新擷取時保留上一份接受資料與其時間；它是歷史接受結果，
不能包裝成這一輪已成功同步。自動化失敗時不能靜默重送舊報表冒充新結果。

### 4.6 規則與人工修正都可重現

保存原始輸入、原文位置、parser 版本、商品設定雜湊及人工決定。
新 parser 或商品設定產生新的解析版本；不覆寫之前已接受的結果，
也不自動沿用舊解析版本的人工審核決定。
同一輸入的重匯不等於禁止重跑新規則。
人工更正必須保留原值、結果、理由與時間，後續報表能回查。

## 6. 風險與處理

| 風險 | 影響 | 首個處理點 |
| --- | --- | --- |
| UIA 只能讀可見文字 | 漏單卻看似正常 | S01 對照人工基準，缺完整性即不可自動接受 |
| 無穩定 ID、同名買家 | 重計、誤併、誤判取消 | S00 身分契約、S04 快照接受與審核 |
| 純文字複製遺失作者或換行 | 訂單歸錯人 | S00 樣本、S03 結構化匯入備援 |
| parser 抽出局部片段 | 將問題或取消文字誤當喊單 | S02 全文文法驗證，不只找 regex 命中 |
| 半途寫入或磁碟錯誤 | 不完整資料成為目前訂單 | S03/S04 交易與回滾測試 |
| CSV 公式注入、個資進 Git | 匯出執行公式或洩漏資訊 | S00 ignore、S05 欄位防護與合成資料 |
| LINE 升級使擷取變動 | 舊 PoC 結論失效 | S01 記錄版本；S08 偵測失效即停止接受 |

## 7. 決策

**建議進入 S00，再做 S01 與手動匯入 MVP。**
自動擷取、改單追蹤與外部整合均保留獨立驗收。
S00 記錄暱稱彙總的風險接受與人工修正邊界；S01/S06 記錄單篇人工整理、匯入、
核對耗時與異常比例，並與原人工流程比較。CLI／JSON 可執行不等於已證明節省時間；
若仍須逐則重打，保留「操作效益未證明」，以真實複製樣本再評估輸入方式。
目前所有功能 SLICE 都尚未開始；這份評估不代表已完成 Gate 0 或實機測試。
